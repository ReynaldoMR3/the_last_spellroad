## 2026-07-27 (2) — Mini-boss engine wiring (backlog 3.4/3.8): boss phase sequencing + Phase-Transition Recovery choice

Ana traced down that the mini-boss content (Warden's 2026-07-21 composition, Pato-validated twice) had never actually been committed to a `wave.json`-equivalent file or wired into the engine — this entry is the engine half only; the content reconstruction into `src/data/waves/boss-1.json` is Ana's/Warden's, logged in their own files.

**Schema:** `WaveDefinition` gained `is_boss?: boolean` (`src/data/types.ts`) so a boss phase can be distinguished from a regular wave without a second parallel data path.

**`SpellroadScene.startWave`:** branches on `wave.is_boss`. Phase 0 of a boss: computes `bossMaxRecoveries = Math.min(totalPhases - 2, MAX_RECOVERIES_HARD_CAP)` (totalPhases counted directly off `this.waves`, not hardcoded), calls `hexcoin.startBossFight()`, and does the one HP reset for the whole fight. Later phases (`wave_index > 0`) skip the HP reset entirely — hp-template.md's damage-threat budget is cumulative across phases, which is the actual reason Phase-Transition Recovery exists; resetting HP per phase would make the fee-gated recovery meaningless.

**`updateEnemies`'s advance logic:** now checks whether the next wave is another phase of the same boss (`next.is_boss && next.level === wave.level`) before auto-advancing. If so, calls the new `startPhaseBreak(nextIndex)` instead. If the boss's last phase just cleared, calls `hexcoin.endBossFight()` and flashes a victory message before falling through to the normal advance.

**`startPhaseBreak`:** flashes the Y/N choice (`FEE_PHASE_RECOVERY` Hexcoin -> `PHASE_RECOVERY_HP_FRACTION` of MAX_HP, or decline), registers one-shot `keydown-Y`/`keydown-N` listeners, resolves by calling `hexcoin.usePhaseRecovery(bossMaxRecoveries)` + `health.restore(...)` on accept, then proceeds to the next phase either way. Guards against double-resolution (`awaitingPhaseChoice` flag) and against the advance-loop re-triggering while the choice is pending (reuses the existing `enemiesRemainingToSpawn = -1` guard pattern from the regular-wave code).

**`handleDeath`:** added `hexcoin.endBossFight()` and clearing `awaitingPhaseChoice` — a mid-fight death shouldn't leave a stale frozen-Hexcoin-snapshot state behind; the next attempt at the boss calls `startBossFight()` again and takes a fresh one regardless, but leaving the old state dangling was sloppy, not necessary to leave as-is.

**Self-verify:** `docker-compose run --rm game npm run typecheck` and `npm run build` both clean. Dev server restarted so the new preload'd `boss-1.json` and the new logic are actually being served, not relying on HMR picking up a brand-new file.

**Not yet verified live:** the actual phase-break prompt, the recovery purchase, and the boss's overall feel/difficulty — self-verify covers compile/build correctness only, same distinction as every other engine entry in this log.

**Status:** `in-progress-with-owner` — self-verified, awaiting developer playtest of the actual boss fight.

## 2026-08-02 (3) — Fix #48: wave/timer race, death-restart inheriting the in-flight wave's monster count

Escalated to Opus per Ana's model-selection row ("escalate for one-off architecture calls") — this is a structural timer/state-machine decision, not a routine fix.

**Root cause, confirmed by reading the code — two defects that compound, not one:**

1. **Nothing invalidated a scheduled callback when the world moved on.** All five `delayedCall` sites in the wave path (`updateEnemies`'s 1200ms advance, `handleDeath`'s 1500ms restart, `startPhaseBreak`'s resolution, `onRangedFire`'s 450ms impact, and every per-enemy staggered spawn timer `WaveLoader.spawnWave` queues) were fire-and-forget, and none cancelled any other. A wave-complete advance scheduled just before a delayed ranged hit killed the player still fired at +1200ms, starting the *next* wave 300ms before the death restart replayed the level from wave 1 — and that next wave's spawn timers, plus the dead wave's own not-yet-fired ones, then spawned into the "restarted" wave 1.
2. **The auto-advance trigger was purely numeric, and `handleDeath` reproduces it exactly.** `enemiesRemainingToSpawn === 0 && enemies.length === 0` is precisely the state `handleDeath` creates when it clears the field, which is why the `-1` sentinel guard didn't hold: the sentinel was overwritten with `0` by the death path itself. This means the extra advance wasn't only reachable via the ranged-shot race — **every** death scheduled a bonus advance on the very next frame, and the ranged shot only determined *which* wave's leftovers were still in flight to be inherited. Worth stating plainly because it widens the reproduction: the developer's ranged-death report is one path into a defect that fires on any death.

**Architecture decision: (a) generation/session counter, plus an explicit phase — not (b) timer-handle tracking.** Both were live options in the issue; the deciding argument is what each one costs against the timers the fix *isn't* looking at:

- (b) requires a registry that is simultaneously **complete** (every timer registered, including the ~6-11 handles `spawnWave` creates per wave inside a loop in a different module, which would have to be plumbed back out and stored) and **selective** (cancel the dead wave's timers, *not* the boss phase-break's — the issue names that trap directly, and a blunt `time.removeAllEvents()` would also take out the ranged impact and every cosmetic tween). Both properties have to be re-established by hand at every new call site forever; a future `delayedCall` added by anyone who doesn't know the registry exists is a silent regression, which is exactly how this bug arrived.
- (a) inverts that. The check lives at the point of *use*, not the point of scheduling, so a callback that forgets to ask is the only failure mode, and it's visible in the callback body being reviewed rather than in an unrelated cancellation site. Selectivity is free and automatic: a generation is taken only when the world genuinely changed (a wave started, or the player died), so the phase-break timer keeps working precisely because nothing bumped the counter under it — no "careful not to cancel that one" special case is needed anywhere. It also scales to the per-enemy spawn timers without plumbing handles: `spawnWave` takes one `isStillCurrent: () => boolean` predicate (required, not defaulted, so a new call site must decide) and checks it inside each staggered callback.
- Cost of (a), stated rather than glossed: stale timers still fire and no-op instead of being cancelled, keeping their closures alive for up to ~1.5s. Negligible at this scale, and I'd rather pay it than own a cancellation registry.

The counter alone does **not** fix defect 2, and that's worth being explicit about since the issue framed it as an either/or: the bonus advance is scheduled *after* `handleDeath` bumps, so it carries a current generation and would happily fire. That half needs a state answer, so `WaveSession` carries a `WavePhase` (`idle`/`running`/`advancing`/`awaiting-phase-choice`/`dead`/`complete`) and the advance is gated on `shouldAutoAdvance(phase, remaining, alive)`, which requires `running`. This also let the two parallel ad-hoc flags it replaces — the `enemiesRemainingToSpawn = -1` sentinel and the separate `awaitingPhaseChoice` boolean, which had to be kept in agreement by hand — collapse into one field with one meaning.

**Pure logic first, TDD, same seam convention as `rangedImpact.ts`/`autoAim.ts`/`waveThreatBudget.ts`/`enemyStatusOverlay.ts`:** wrote `src/systems/waveSession.test.ts` against the not-yet-created module (confirmed red — `vitest` failed to resolve `./waveSession`), then implemented `src/systems/waveSession.ts`: the `WaveSession` class (monotonic `generation`; `beginWave()`/`beginDeath()` bump and return a token; `beginAdvance()`/`beginPhaseChoice()`/`markComplete()` change phase without bumping; `isCurrent(token)`) and the pure `shouldAutoAdvance` gate. Green, 14 new tests, 49/49 total.

**Scene/loader wiring:** `SpellroadScene` gained a `session` field (constructed in `create()` with the other run systems). `startWave` takes a generation and threads it into `spawnWave`'s new predicate; the out-of-waves branch calls `markComplete()`. `updateEnemies` calls `shouldAutoAdvance(...)`, then `beginAdvance()` in place of the `-1` sentinel, captures `nextIndex` at schedule time, and guards the 1200ms callback. `startPhaseBreak` captures (does not bump) the generation, uses the phase for its double-resolution guard, and guards its resolution timer. `handleDeath` calls `beginDeath()` as its very first statement — before any state is cleared — and guards its restart timer; `awaitingPhaseChoice` is deleted. `onRangedFire`'s impact timer is generation-tagged too, so a shot in flight across a death can't land on the respawned mage — the same class of bug, reachable from the same playtest, and #47's fix (commit e8eb527, untouched here) is unaffected: the live-position recheck still runs, it just no longer runs at all for a shot whose world is gone. Cosmetic tweens (projectile dot, damage numbers, debuff pulse) are deliberately left unguarded: they self-destroy and touch no game state.

**Why this verification would actually catch a regression of this specific timing-race class (per ADR-0001), and where it can't:** the honest limit first — Vitest here runs no Phaser clock, so **no test in this repo proves anything about real `delayedCall` interleaving**, and I'm not claiming otherwise. What the tests do prove is the part that was actually wrong, which is decision logic, not scheduling. The race's two failure modes are both expressible without a clock and both are asserted directly: (1) `shouldAutoAdvance("dead", 0, 0) === false` — the counters-look-cleared-because-death-cleared-them case, the exact condition that defeated the `-1` sentinel; a future edit that reverts to a numeric-only trigger, or lets `handleDeath` leave the phase `running`, fails that test. (2) A token captured before `beginDeath()` is no longer current, and generations are never reused, asserted over a 10-transition sequence — so an edit that made `beginDeath` non-bumping, or made `beginAdvance` bump (which would wrongly kill the phase-break timer), fails. Those are wiring and runtime questions, and only the playtest below settles them.

## 2026-08-02 (5) — Code-review addendum: a real #47/#48 interaction, flagged not fixed

`/code-review` on the combined #47+#48+#49 branch (Spec axis) caught a genuine cross-fix interaction neither ticket's own scope covered: `startPhaseBreak`'s decline path (`resolve(false)`) schedules `startWave` only 200ms later, which is *shorter* than `RANGED_TRAVEL_MS` (450ms, #47's impact-recheck window). ## 2026-08-04 — Fix: road art goes fully black after Quit to Title -> New Game

Developer's first real playtest of PR #83 (merged into `ana/playtest-08-03-feedback`) found a real bug the sandboxed browser pane's frame-pump verification couldn't have caught: HP/Mana bars, the onboarding hint, cast effects, and the Mana-warning styling all confirmed working, and the 8/sec regen retune "feels right" (no change needed) — but "after quit to title and new game, the screen turns fully black, you can still move and hit, but the spellroad is all black, the only visible items are the mage, the monsters, the spells and the text."

**Root cause.** Before backlog 5.8 added a real Quit-to-Title/New-Game restart path, `SpellroadScene.create()` only ever ran once per page load — Phaser reuses the same Scene *instance* across `scene.start()` calls, it does not recreate the class from scratch, so any mutable field not explicitly reassigned inside `create()` silently carries its value from the previous life into the next one. `renderedLevel` (the guard `renderLevelArt` uses to avoid rebuilding the same level's Tiled layer on every `startWave()` call, including phase-breaks within one boss fight) is exactly such a field: it starts at `0` only via the class-field declaration, evaluated once at object construction, never reset in `create()`. A fresh restart's first `startWave(0)` calls `renderLevelArt(1)`; if the player's previous life ended on Level 1 (the common case — dying or quitting early, exactly what a developer smoke-testing the new Pause/Quit flow would do), `renderedLevel` is still `1` from that life, so the guard's `if (this.renderedLevel === level) return;` fires immediately and skips building a tile layer at all for the new scene instance — leaving only `createRoad()`'s near-black placeholder rect (`0x11131a`) visible, exactly matching the report (everything drawn by `create()`'s other methods — mage, HUD, enemies, spell effects — renders fine, since those genuinely do get freshly created every `create()` call; only the tile art, gated by this one stale field, silently no-ops).

**Same class of bug, one more confirmed instance with a real (if not yet visible) gameplay consequence:** `highestLevelReached` has the identical staleness bug — `HexcoinSystem.markLevelStart()` only fires the first time a level number is crossed (`if (wave.level > this.highestLevelReached)`), so a stale non-zero value surviving from a deeper previous run would silently skip re-arming the Hexcoin income floor on whatever level the new run actually starts at. No visible symptom reported yet (this needs a death/checkpoint scenario after a restart to surface), but it shares the exact same root cause and needed the same fix.

**Fix (`SpellroadScene.create()`):** explicit resets added for every mutable field this class of bug can reach — `renderedLevel`, `currentLevelTilemap`, `currentLevelLayer`, `enemies`, `enemiesRemainingToSpawn`, `waveIndex`, `highestLevelReached`, `bossMaxRecoveries`, `previewSpellId`, `previewLockedEnemy`, `phaseChoiceListeners`, `lastFacing`, `lastPointerActivityAt`, `messageClearAt` — not just the one field that happened to produce a visible symptom. This mirrors a precedent already in the same method: `this.session = new WaveSession()` was already commented "constructed with the rest of the run's systems so a scene restart gets a clean generation/phase, not one inherited from the previous run" (issue #48) — that principle just hadn't been applied to every other stateful field once 5.8 made "scene restart" a real, reachable scenario instead of a hypothetical one.

**Self-verify:** `docker-compose run --rm game npm run typecheck`/`npm test` (230/230)/`npm run build` all clean. Reproduced the exact bug live first (temporary `window.__game` debug hook + manual `game.loop.step()` frame-pump, same technique as the prior entry, needed for the same sandboxed-pane `document.visibilityState: "hidden"` reason): confirmed pre-fix that a fresh Level-1 life followed by Quit-to-Title -> New Game left `renderedLevel` at a stale `1` with no tile layer; confirmed post-fix that the identical sequence now leaves `renderedLevel: 1`, `currentLevelLayer`/`currentLevelTilemap` both present, `enemies.length` correctly reset to the fresh wave's count, and `highestLevelReached: 1` (not stale) — and a live screenshot of the second life shows the road art rendering identically to the first. Debug hook removed before finalizing, same as the prior cycle.

**Status:** fix `in-progress-with-owner`, self-verified and live-reproduced/confirmed by Loomwright; still needs the developer to re-confirm the exact reported repro (quit-to-title, new game, look at the road) in a real session before this counts as `shipped-and-validated`. ## 2026-08-09 — Backlog 1.6 follow-up: final review found two save-scum bugs, fixed

A final whole-branch review of the SaveSystem wiring above (Tasks 5-8) — looking at all four

1. **Hexcoin level-floor ratchet exploit.** `writeCheckpoint()` wrote `hexcoinBalance` from
   both the level-start call site (a genuine floor, correct) and the Mastery tier-up call
   site (a mid-level balance, not a floor — wrong). `SpellroadScene.create()`'s
   `hexcoin.restoreBalance(saved.hexcoinBalance)` on `Continue` sets whatever was saved as
   the new floor. Concrete exploit: earn 20 on Level 2 → tier-up saves `hexcoinBalance: 20`

   `mastery.applyRandomDeathPenalty()` and `hexcoin.rollbackToLevelStart()` but never called

   Mastery Loss" pillar, the same pillar `run_report.md` cited as criterion 3 for picking
   this backlog item.

- `handleDeath()` now calls `writeCheckpoint()` right after `hexcoin.rollbackToLevelStart()`,
  closing the escape hatch.

### Issue #167 — three root causes, all in the *invocation*, one dominant

1. **Separation applied only on the settled/hold-range branches.** The chase, retreat, and wall-slide branches each called `body.setVelocity` with a raw steering vector and no separation at all. ### Issue #182 — phase-break and Side-Pocket Y/N prompts auto-cleared while still unresolved

Confirmed the exact mechanism the ticket described: `startPhaseBreak` and `startSidePocketChoice` both render their Y/N (or E/C) prompt via `flashMessage(text, 60000, "warning")` — a **fixed 60-second display duration** — while the actual choice is resolved by `keydown-Y`/`keydown-N` (or `keydown-E`/`keydown-C`) listeners armed with **no expiry** (`this.input.keyboard?.once(...)`). `update()`'s generic clear check (`if (this.messageText && this.time.now > this.messageClearAt) { this.messageText.setText("") ... }`) doesn't know or care whether a choice is still pending — it fires purely on the clock. A player who takes longer than 60s to decide (reading, AFK, or a pause/resume — the developer reproduced both) sees the prompt vanish while the game is still genuinely blocked waiting for a keypress, with nothing on screen explaining why.

**Fix:** all three of this exact call shape's `flashMessage` invocations (the phase-break prompt, the Side-Pocket Explore/Continue prompt's initial render, and its "already explored" re-render after Explore) now pass `Infinity` as the duration instead of `60000`. `update()`'s `this.time.now > this.messageClearAt` can never trip while `messageClearAt` is `Infinity`, so the prompt persists exactly until the choice resolves — at which point `resolve()`'s own follow-up (`flashMessage("Recovered ... HP", 1200)`, the next wave's level/phase flash, etc.) naturally overwrites `messageText` with a real, finite duration. No new field, no special-cased branch in `update()` — the existing "durationMs" parameter already expressed exactly what an indefinite hold needed, once handed the right value.

**Checked the other call sites the ticket named, and they don't share this bug:** `TitleScene.promptNewGameOverwrite` and `PauseScene.promptQuitConfirm` both render their Y/N confirm text on their own dedicated `confirmText` element, created fresh per prompt and `.destroy()`ed only by their own `cleanup()` closure when `onY`/`onN` fires — neither scene has an `update()` method at all, so there is no generic timer anywhere in either file that could auto-clear it. They reuse this repo's Y/N *visual* pattern (the `startPhaseBreak`-style message + `keydown-Y`/`keydown-N` pair, per their own doc comments), but not the specific `flashMessage`/`messageClearAt` *auto-clear* mechanism issue #182 is actually about — so nothing there needed changing, and I didn't touch either file.

**Left every other `flashMessage` call site untouched, on purpose:** "Hit!" (300ms), "Not enough Mana" (900ms), "Recovered ... HP" (1200ms), the level/phase-transition flashes, "Vertical slice complete!" (3000ms) — all plain informational messages with no pending keyboard choice behind them — keep their original finite durations. Auto-clearing on a timer is exactly correct for those; the bug was specific to the handful of calls that also gate an indefinite `.once()` listener, and this fix touches only those three.

### Where the interlude starts and stops, and why there rather than somewhere else

Two judgment calls the ticket flagged as needing an explicit answer rather than a silent one.

**It starts the instant a wave clears, not when the Side-Pocket prompt appears.** The call sits in `updateEnemies`'s `shouldAutoAdvance` branch, on the line immediately after `stopCombatCue()` and before the four branches that decide what actually follows (boss phase-break, Side-Pocket prompt, boss victory, plain 1200 ms auto-advance). The Explore prompt is the moment the developer *noticed* the silence, but it is one of those four branches and it appears at most four times in the entire slice; the silence is every non-combat gap. Starting on the clear scores all four branches from one line, needs no second trigger inside `startSidePocketChoice`, and reads as a single rule — no monsters on the road, exploration music plays — instead of a special case. #142's own comment at that site already noted the Side-Pocket prompt was "read in quiet"; it no longer is.

**It stops on the next wave's first enemy spawn, not when Continue is pressed and not at `startWave`'s top.** That is the exact line that starts the combat cue (`spawnWave`'s spawn callback), so the two tracks hand off with no gap in either direction — the road goes from interlude to combat the instant a monster exists, and back the instant the last one dies. Stopping at `startWave`'s top instead would reintroduce a smaller version of the same silence: waves stagger their spawns (`spawn_delay_ms`), so there is a real window there with no enemy on screen. The stop is unconditional, ahead of `shouldPlayCombatCueForWave`'s boss check, because "an enemy exists" ends the interlude regardless of what kind of wave it is.

**It plays in every non-combat gap within a level, not only where a Side-Pocket encounter happens to be.** The ticket flagged this as a scope call; this is the broader reading, on the grounds that the underlying complaint is silence and the prompt is only where it surfaced. The narrower alternative would have left the great majority of between-wave gaps silent while scoring four specific moments, which is a stranger rule to explain than the general one.

**Boss waves are excluded on both sides.** `shouldPlayExplorationLoopBetweenWaves(clearedWave, nextWave)` returns false if either is a boss wave, so the Director trial's theme keeps sole ownership of Level 5 from Phase 1 through victory including its phase-breaks — the same mutual exclusion `shouldPlayCombatCueForWave` already establishes, extended to a third track. The `nextWave` half also means the last ordinary wave of Level 4 does not open a 1.2-second exploration window immediately before the boss theme starts; that transition is the run's biggest tonal gear-change and a one-second track between its halves would blunt it. A missing next wave (the end of the slice) is excluded for the same reason — nothing follows, so there is no interlude, only an ending.

### The rotation

`pickExplorationTrack(previousKey, allKeys = EXPLORATION_LOOP_KEYS, random = Math.random)` in `systems/bgm.ts` — pure, Phaser-free, unit-testable, same convention `shouldPlayCombatCueForWave` set, with the random source injected as a parameter so the rotation is testable without stubbing globals. It filters out whichever key played last and picks uniformly among the rest; `undefined` previous (first interlude of a session) means all three are eligible. Degenerate inputs fail safe rather than throwing: a one-track list returns that track, an empty list returns `undefined` and the scene skips playback rather than taking a level down over a music choice. The index is clamped, so an injected double (or a seeded RNG swapped in later) returning exactly `1` can't index off the end.

Random rather than a fixed A-B-C cycle, deliberately: a fixed cycle is itself a longer loop a player eventually learns, and the only property the ticket actually asks for is no immediate repeat.

The scene holds `lastExplorationTrackKey` and hands it back in. Because `playExplorationLoop` is a no-op while something is already playing, the rotation only advances when an interlude genuinely stopped and started again — which is exactly "each time it starts up again after having stopped," with a wave's combat as the thing that separates two interludes. Back-to-back short waves therefore can't cut the same track's opening bar over and over.

### Everything else in the wiring

- `EXPLORATION_LOOP_KEYS` / `EXPLORATION_LOOP_URLS` in `bgm.ts` — the first keyed collection in that module. Its own doc comment previously said to introduce the union/lookup pattern "when a track ships that a caller genuinely selects *by key* at runtime"; this is that track, so it ships keyed while the boss theme and combat cue stay the flat single-track exports they were.
- `EXPLORATION_LOOP_VOLUME = 0.5`, matched to `COMBAT_CUE_VOLUME` rather than chosen independently. The two hand off to each other continuously within a level, and a level difference across that handoff would read as the game getting louder or quieter at the moment combat starts — a second, unasked-for signal on top of the deliberate one the track change already carries. Still below every SFX one-shot's 0.85 floor, per #97's original criterion.
- All three tracks are preloaded eagerly at scene boot, not lazily on first pick: the pick happens on the frame a wave clears, and a ~650 KB fetch there would put a stall on the exact instant the road goes quiet.
- Stops on `handleDeath` (a death during an interlude is a real state — a ranged shot already in flight can land in the gap), on the scene-restart reset block (quitting to Title from the Explore prompt is a state a player can sit in indefinitely, so this is the track most likely to still be playing at a restart), and on the `SHUTDOWN` safety net alongside the other two. `lastExplorationTrackKey` resets with the restart so a fresh run's first pick isn't biased by an abandoned one.

## 2026-08-13 — Click-to-arm + scroll-wheel hotbar cycling (issue #198)

Two playtesters asked for mouse-preferred spell selection alongside the existing 1-6 number
row. Developer scoped both halves together: clicking a hotbar slot arms it, and the mouse wheel
cycles the armed slot forward/backward with wrap-around. Both route through the exact same
`handleHotbarPress(index)` the number-key handler (`createInput`) already calls — no second
"arm spell" path exists anywhere in this change.

**Pure logic first, TDD, same seam convention as every other module in this file**
(`src/systems/hotbarLayout.ts` + `.test.ts`, 28 tests total, 15 new):
- `hotbarSlotIndexAtPoint(rects, x, y)` — point-in-rect hit test against the same
  `HotbarSlotRect[]` `computeHotbarSlotRects` already produces for rendering, so the click
  target and the rendered slot boundary can never drift apart. Returns `null` (not `-1`) for a
  miss, so a caller can't mistake "no slot" for "slot 0" via truthiness.
- `nextHotbarIndex(currentIndex, slotCount, direction)` — wraps at both ends; `currentIndex < 0`
  ("nothing currently armed") is handled as an explicit branch rather than folded into the
  modulo arithmetic, since encoding "none" as a sentinel and wrapping through it lands one slot
  short of the true last index (confirmed by hand before writing the test, not guessed past).

**`SpellroadScene.ts` wiring:**
- The existing `pointerdown` handler (`createInput`) now hit-tests `pointer.x`/`pointer.y`
  against `this.hotbarSlotRects` *before* its `leftButtonDown`/`rightButtonDown` branches. A hit
  calls `handleHotbarPress(index)` and returns — it never falls through to `confirmCast`. This
  is a small correctness improvement beyond the ticket's own ask: before this change, any
  left-click anywhere (hotbar included) called `confirmCast(pointer.worldX, pointer.worldY)`, so
  clicking the hotbar while a spell was already previewed would have fired a cast aimed at the
  HUD's own screen position instead of arming/confirming the slot that was actually clicked.
  Used `pointer.x`/`pointer.y` (screen space, already scale-corrected by Phaser for `Scale.FIT`)
  rather than `pointer.worldX`/`worldY` — deliberate, since `hotbarSlotRects` is laid out in the
  same screen space the HUD's `Text`/`Graphics` objects use, not a world space affected by
  camera scroll (this scene never scrolls its camera, so the two are numerically identical
  today, but screen space is the *correct* one to test against here regardless).
- A new `wheel` listener (`this.input.on("wheel", ...)`, also in `createInput`) finds the
  currently-previewed spell's index in `equippedSpells` (`-1` if none), computes
  `nextHotbarIndex` against `hotbarSlotRects.length` (the full rendered 1-6 row, not
  `equippedSpells.length` — a trailing empty slot is a valid, no-op stop in the cycle, exactly
  like clicking or number-keying an empty slot already is a no-op), and calls
  `handleHotbarPress(nextIndex)`. Scroll-down (`deltaY > 0`) moves forward, scroll-up moves
  backward — an arbitrary but internally consistent choice; neither the issue nor any existing
  convention in this codebase specifies a direction.

**Self-verify:** `docker-compose run --rm game npm run typecheck`, `npm run build`, and
`npm test` all clean — 332/332 across 30 files (up from 319; `hotbarLayout.test.ts` goes 13 → 28
tests). Docker was available and used throughout; no host fallback needed. Dev server smoke
check not performed live this entry — port 5173 was already bound by another running session's
container at self-verify time (same recurring caveat as several earlier entries in this file);
did not reuse that other session's container since it wouldn't reflect this branch's code.

**Judgment calls made, flagged rather than silently decided:**
- **Wrap-around direction and scroll-direction mapping** are arbitrary (see above) — the issue
  only requires wrapping at both ends and cycling, not a specific up/down-to-forward/backward
  mapping. Easy to flip (`direction: 1 | -1 = deltaY > 0 ? 1 : -1` is the one line to invert) if
  a developer playtest finds it backwards from expectation.
- **Currently-armed highlight state:** already existed before this ticket — `updateHotbar`
  already draws a distinct border (`isArmed` check) for whichever slot's spell equals
  `previewSpellId`. Click-to-arm and scroll-cycling both set `previewSpellId` through the same
  `handleHotbarPress` call the number-key path already used, so the existing highlight updates
  for all three input methods with no separate code needed — not a new decision, just confirmed
  it falls out of the existing highlight logic for free.
- **Scrolling while a spell is already mid-preview:** `handleHotbarPress(nextIndex)` does not
  auto-confirm or auto-cancel the *previous* preview before arming the new one — it just
  overwrites `previewSpellId`, exactly like pressing a different number key mid-preview already
  did before this ticket (e.g. hotkey `1` then, without confirming, hotkey `2`). Scroll-cycling
  reuses that pre-existing behavior rather than inventing a different one for the mouse-wheel
  path specifically.
- **No debounce/threshold on wheel events:** a single native mouse-wheel detent normally fires
  one `wheel` event, but a trackpad's continuous scroll can fire many in quick succession, each
  advancing the cycle by one slot — this could feel like it's spinning past several spells for
  what was meant as "nudge it over by one." Not addressed here since the issue is scoped to
  mouse-wheel ergonomics specifically and the ticket didn't ask for trackpad-specific tuning;
  flagging it as a real possible follow-up rather than guessing at a debounce window unasked.

**Not yet developer-confirmed:** whether click-to-arm and scroll-cycling actually feel good in
