**Action:** `docs/agents/_reference/engine-contract.md` and `docs/agents/loomwright/AGENT.md` need one sentence added extending scope to "runtime execution of HP, Mana, Mastery, Hexcoin, and Debuff mechanics per Pato's templates" before Task 1.1 below can be dispatched as in-scope work. **Status:** `shipped-and-validated` — engine-contract and `loomwright/AGENT.md` edited 2026-07-23; Phase 1 tasks below dispatched against the new scope. Still overridable by the developer at any time; nothing here forecloses that.

### 0.2 — Checkpoint/retry Hexcoin income-bounding (developer decision, genuinely open)

Does a death respawn place the mage *before or after* the pre-boss waves, and do those waves re-award Hexcoin on retry? The forward-only rule and the Phase-Transition Recovery fee are both priced against a bounded per-expedition Hexcoin income (see GDD "Open Design Questions," item 6) — if retried waves re-pay Hexcoin, that bound doesn't hold.

**Blocks:** Task 1.6 (checkpoint/respawn placement implementation) directly. Does not block anything earlier in the sequence.

**Status:** `shipped-and-validated` — resolved 2026-08-01. Developer's decision: respawn at the first wave of the *current level*, and retried waves re-award Hexcoin normally (no suppression). Implemented in `SpellroadScene.handleDeath()`: respawn index now looked up via `this.waves.findIndex((w) => w.level === currentLevel)` instead of a hardcoded `startWave(0)`. **First implementation had a real BLOCKING bug, caught by Heckler's same-day critique and fixed before this row closed:** calling `hexcoin.resetExpedition()` (zero the balance) on every death, combined with forward-only progression, permanently locked the mage out of the 30-Hexcoin Fee 2 the instant a death happened in or after Level 4 (that level's own 25-kill budget is below the fee, with no way to earn the gap back). Fixed with a floor instead of a hard reset: `HexcoinSystem.markLevelStart()`/`rollbackToLevelStart()` — a death rolls back only the current level's own partial gains, never below what was already banked from levels genuinely cleared, while still bounding what one retry can add. See `docs/agents/_reference/hexcoin-template.md` and the GDD's Gameplay Loop, "Checkpoint granularity, resolved 2026-08-01." This also unblocks Task 1.6's design question, though 1.6 itself (full `SaveSystem` cross-session wiring) remains separate, larger, not-yet-built work.

### 0.3 — All-Novice-hotbar exploit (developer decision, not blocking)

2026-07-23 review found the Novice-floor mercy rule (death costs no Mastery if every equipped spell is already Novice) creates a zero-cost way to farm boss-pattern knowledge with an all-Novice loadout. Two known resolution shapes exist (narrate it as an in-fiction "the Director doesn't bother punishing the unskilled" mechanic, or make death cost something else when the roll finds no eligible spell) — developer has not chosen either.

**Blocks:** nothing currently scheduled. Tracked so it doesn't silently drop before Lorena's narrative pass (Phase 4) or before Heckler's pre-submission review (Phase 5), either of which could plausibly need the answer.

**Status:** `shipped-and-validated` for the content — resolved 2026-08-01. Developer's decision: narrative resolution, no new mechanical penalty. Lorena reframed the death flash message (`"Died — no Mastery lost; the Road grades what you've grown"`, extending the Invigilator's established "testing, not cruelty" framing) and added a supporting bullet to `lore-premise.md`'s Established Named Facts. Wired directly into `SpellroadScene.handleDeath()`. See `docs/agents/lorena/log.md`, 2026-08-01 (2). Closes backlog task 4.3 too — see that row.

### 0.4 — Mastery growth rate (developer decision, sequenced not blocked)

How many landed casts/kills per Mastery tier. Developer's 2026-07-22 call was to wait for Warden's real regular-wave data rather than guess a placeholder (GDD, "Open Design Questions").

**Corrected 2026-07-23, after Task 2.4's wave data actually landed:** "wait for Warden's data" means enough wave data across multiple levels to size a real curve — not literally the first wave batch. Level 1's 3 waves (18 enemies total) is too small a sample; Pato checked the arithmetic and found a naive rate sized off it alone would cap most of the spellbook at Master within a single level. See `docs/agents/pato/log.md` (2026-07-23 (4)) and `docs/agents/_reference/mastery-template.md` for the full reasoning. `src/systems/MasterySystem.ts` carries an explicitly-flagged engine-testing placeholder (5 landed casts/tier) in the meantime — not a design number.

**Status:** `shipped-and-validated`, closed 2026-07-25. Warden's Level 2/3 wave batch (Task 3.3) supplied the 2-3 levels' worth of data this needed (60 enemies across Levels 1-3). Pato's first pass (20 casts/tier) assumed 1 landed cast ≈ 1 kill; Heckler's critique found that false (a weak spell needs several casts per kill) and reproduced the exact failure mode being guarded against via a different mechanism. Pato re-derived correctly against actual casts-to-kill and landed on **180 landed casts/tier**, wired into `MasterySystem.ts`. See `docs/agents/pato/log.md` (2026-07-25 (3) and (4), the latter superseding the former's Part 2) and `docs/agents/heckler/log.md` (2026-07-25).

### 0.6 — Mastery re-grinding via repeated level retries (new, found 2026-08-01, not blocking)

Combining 0.2's resolution (a death respawns at the current level's start and re-awards Hexcoin/kills on retry) with 0.5's resolution (Mastery progress is now kill-gated, sized against a single level's enemy count as the worst-case ceiling) opens a residual neither fix closes alone: "one level's enemy count" is no longer a hard reachability ceiling once that level can be retried indefinitely via repeated deaths. A patient player could out-grind Level 4's 25-kill cap (`docs/agents/_reference/mastery-template.md`'s new derivation) across multiple attempts at it, rather than needing to progress through new content.

Death's own Mastery-tier-drop penalty partially self-limits this in practice — a loadout with the grinding spell as its only non-Novice equipped spell guarantees the random death-roll always hits exactly that spell, undoing the grind at the same rate it's being farmed — but this hasn't been checked as an airtight bound against a mixed loadout (2+ non-Novice spells diluting the roll's odds of hitting the target), which is genuinely probabilistic territory, not another worst-case constant to compute.

**Blocks:** nothing currently scheduled — same reasoning as 0.5's own original entry (no live opponents yet meaningfully exploitable at scale). Tracked for Phase 5's adversarial QA pass (5.7).

**Status:** `blocked-with-reason`, non-urgent, re-raised at Phase 5 alongside 0.3/0.5.

### 0.7 — Screen-flow/UI-shell ownership gap (developer decision, resolved 2026-08-01)

**The gap:** found while scoping the Boot/Title/Pause screens via `/grill-with-docs` — no agent owns scene wiring or UI shell at all. Loomwright's charter (`docs/agents/_reference/engine-contract.md`) covers movement/casting and (per 0.1) HP/Mana/Mastery/Hexcoin/Debuff runtime, but nothing about scenes, menus, boot, or pause. Confirmed via `grep` across every `AGENT.md` and this backlog: zero hits for scene/menu/pause/boot/title.

**Decision:** Loomwright's engine scope extends to cover this — same pattern as 0.1's extension, a scope clarification rather than a new design decision. See the GDD's new "Screen Flow And Pause" section (after Core Controls And Casting) for the full design: Boot/Preload → Title → gameplay scene chain; Title offers New Game (no save) or Continue/New Game-with-confirm (save exists); pause is a hard pause (`scene.pause()`) triggered by a contextual `Esc` (cancels an active spell preview first, opens/closes pause otherwise), offering only Resume and Quit to Title, both quit paths confirming since they can lose un-saved progress. No Options/Settings menu in the slice.

**Action:** `docs/agents/_reference/engine-contract.md` and `docs/agents/loomwright/AGENT.md` updated 2026-08-01 with the scope extension. Full design detail recorded in `docs/superpowers/specs/2026-08-01-boot-title-pause-screens-design.md`. Build task tracked as 5.8.

**Status:** `shipped-and-validated` for the scope decision and design — contract docs and GDD updated. The actual build (5.8) is separate, not-yet-built work.

### 0.5 — Mastery farming via non-lethal hits (new, found 2026-07-25, not blocking)

While verifying 0.4's corrected number, found that `MasterySystem.recordLandedCast` fires on any successful hit, not a kill — so a player who deliberately keeps landing non-lethal hits on a single enemy isn't bounded by level content at all, only by real time. No finite per-tier number closes this (0.4's 180 only bounds the "clear the level normally" case); it needs a mechanic change (e.g., gate progress on kills instead of hits) rather than a resize, which is a design call, not something to guess mid-session.

**Blocks:** nothing currently scheduled — the vertical slice has no live opponents to defend against this kind of exploit yet. Tracked so it doesn't silently drop before Phase 5's adversarial QA pass, the natural place this class of finding belongs (same shape as item 0.3).

**Status:** `shipped-and-validated` — resolved 2026-08-01. Developer's decision: "gate on kills instead." `MasterySystem.recordLandedCast`'s call site (`SpellroadScene.confirmCast`) now gates on `kills > 0` instead of `hits > 0`, closing the non-lethal-hit farming vector outright. This changed the counted unit from casts to kills, invalidating the prior 180-casts/tier number — recomputed against real per-level enemy counts (Level 4 = 25, the new single worst level) to **24 kills/tier** (48 to fully master), ~1.92x margin against Level 4 alone. Full derivation: `docs/agents/_reference/mastery-template.md`, "Resolved 2026-08-01." **New residual, not fixed, explicitly carried forward for Phase 5 (5.6's own row):** item 0.2's resolution (same day) lets a death retry the current level indefinitely, so "one level's enemy count" is no longer a hard ceiling the way it was when death ended the whole attempt — a patient player could out-grind Level 4's cap across repeated retries. Not a fresh guess-and-hope; flagged plainly as unresolved, needing a probabilistic check rather than another worst-case constant.

## Maintenance rules for this file

- Update a row's `Status` the moment an agent reports back to Ana — do not batch updates.
- When a row moves to `blocked-with-reason`, state the reason inline in that row's table cell or in a linked note above the table (as Phase 0 does) — never leave a row silently stuck.
- Adding a task later: append it to the relevant phase table with a new ID (`<phase>.<next-number>`), don't renumber existing IDs — other rows' `Depends on` references would break.
- This file does not replace `ana/log.md`. The log stays the narrative history of *why* a decision was made; this backlog is the current-state tracker of *what's left*. Cross-link them (a log entry can say "see backlog 3.4"; a backlog row doesn't need to restate log detail).
