## 2026-07-24 (2) — First real developer playtest (backlog task 2.6), via the just-fixed Docker path: 1 BLOCKING crash found and fixed, 2 UX/design gaps opened

The developer used the previous entry's fix to actually run the game (`docker-compose up game`, real browser at `localhost:5173`, not the sandboxed pane) and gave feedback directly, three items, verbatim substance preserved rather than summarized into a vibe:

1. "I don't understand how to point the spells... not clear if the spell is really hitting the targets, I see my HP going down, but the monsters HP not."
2. "The monsters and the spells seem to go out of the spellroad, the purple lane, so feels off, also I need to point with the trackpad... difficult to play."
3. "I was able to finish 2 monsters and win 2 hexacoins, but after my HP got to 2, then no reset, or anything, just a crashed game" (recovered with a hard reload).

Did not take this at face value or dispatch it blind — investigated each against the actual code before writing anything into the backlog, per my own dispatch procedure's rule that every task must reference a real, checked scope, not an improvised guess.

**Item 3 (the crash) — root-caused and fixed, not just logged.** This is the one item that's a correctness bug rather than a design gap, and it was blocking further play, so I used the `systematic-debugging` process rather than patching on a guess: read `HealthSystem.applyDamage`/`handleDeath`/`updateEnemies` (`src/scenes/SpellroadScene.ts`, `src/systems/HealthSystem.ts`), formed a specific hypothesis (death mid-iteration of `updateEnemies`'s `for` loop causes `handleDeath()` to destroy an enemy the loop hasn't reached yet, and Phaser nulls that enemy's Arcade `body` on destroy), then **reproduced it directly against the live Docker dev server** rather than trusting static reading alone — a temporary debug hook in `main.ts` (reverted before committing, same pattern as the 2026-07-23 mouse-bypass precedent) exposed the Phaser game instance to the browser console, and Vite's dev server let me `import()` the real `Enemy` class module directly, so I could construct real enemies and call the real (TypeScript-private-but-runtime-public) `updateEnemies` method with a controlled HP/enemy-count setup. First run threw exactly the predicted error: `TypeError: Cannot read properties of undefined (reading 'setVelocity')` at `Enemy.update`, called from `SpellroadScene.updateEnemies` — confirming the hypothesis with an actual stack trace, not just plausible reasoning.

Fix: `updateEnemies` now snapshots the array before iterating (`[...this.enemies]`, the same defensive pattern `confirmCast` already uses a few methods above it, for the identical reason) and skips any enemy whose `.active` is `false` by the time the loop reaches it. Re-ran the identical repro post-fix: no throw, HP and enemies reset correctly. Also ran a second script confirming ordinary no-death multi-enemy updates are unaffected (both enemies stay `active`, keep updating normally). `docker-compose run --rm game npm run typecheck` and `npm run build` both clean post-fix. Full detail: backlog item 2.8.

**Items 1 and 2 — confirmed real against the code, not dispatched for a fix.** Both are genuine gaps, not user error or a display bug hiding a working number:

- Item 1: `Enemy.hp` (`src/entities/Enemy.ts`) is tracked but never rendered anywhere — no HP bar, no text, no tint. The only cast-related flash message (`"Hit!"`) is wired to the *player* getting hit (the `HealthSystem` constructor's second callback in `SpellroadScene.create()`), not to the player landing a hit on an enemy. A non-lethal hit produces zero observable feedback today, which is exactly what was reported.
- Item 2: two separate confirmed gaps. The mage's physics body is explicitly clamped to the lane rectangle (`createMage`'s `body.setBoundsRectangle`), but `Enemy.ts` only sets Phaser's default `setCollideWorldBounds` (the full canvas) — no lane clamp exists for enemies. Separately, `SpellCaster.ts`'s shape geometry (line 220px, cone radius 180px, circle radius 90px) has zero clamp against the lane rectangle (only 160px tall), so an off-horizontal aim visibly draws outside the purple lines. And targeting direction is read entirely from `this.input.activePointer` with no non-mouse fallback anywhere in `updatePreview`/`confirmCast` — confirmed, not assumed, by reading both call sites.

**Deliberately not fixed by me right now, and not silently guessed at either:** both are real UI/design decisions (what should enemy-hit feedback look like — bar, tint, floating number, some mix; what should the non-mouse aiming default be — last-move-direction, nearest-enemy auto-target, something else) that aren't covered by `engine-contract.md`'s current scope, and improvising an answer here would be exactly the kind of on-the-spot scope invention my own dispatch procedure exists to prevent (same reasoning as the 2026-07-21 entry (4) precedent). Logged as backlog items 2.9 and 2.10, both `blocked-with-reason` pending a developer call, both explicitly re-raised rather than left to fall off the list.
