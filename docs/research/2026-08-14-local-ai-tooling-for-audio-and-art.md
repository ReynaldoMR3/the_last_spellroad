# Local AI tooling for audio and art: is it the right lever?

Date: 2026-08-14
Scope: whether local/open-weight generative AI models (music/audio and pixel-art image generation) are a practical upgrade over the current pipeline, given the developer's rejection of a recent Composer music revision.
Machine: MacBook Air (M1, 8 CPU cores, 8 GB unified memory), Docker-only per [ADR 0003](../adr/0003-docker-only-rotating-creative-prototypes.md), no GPU passthrough (Docker Desktop/VM on macOS runs Linux containers CPU-only — no Metal).
Status: research only; no models downloaded, no code changed.
Related prior research: [2026-08-07 local creative models inventory](2026-08-07-local-creative-models.md) (already concluded neural audio/most diffusion models don't fit this Mac) and [2026-08-07 CC0 art/audio research](2026-08-07-creative-commons-art-audio.md). This doc re-verifies those conclusions against primary sources for the audio side and adds the mixing/soundfont angle the rejection specifically raised, which the prior docs didn't cover.

## Direct recommendation (answers Q5 first)

**Local generative AI is not the right lever here. Fix the mixing and the soundfont first — both are classical DSP/asset-swap problems, solvable in hours, with a local model's-worth of effort buying almost nothing on an 8 GB CPU-only Mac.**

The developer's three rejection reasons split cleanly:

1. "Notation/composition choices weren't great" — a musical-judgment problem. No model discussed below fixes this; it needs a better brief or better composition, not different tooling.
2. "Mixing was off" — this is exactly what CC10 (pan) / CC7 (volume) MIDI events and an `ffmpeg`/DAW-style gain-staging pass fix. It requires no new model, no GPU, no new dependency beyond what `tools/composer/Dockerfile` already has (`music21`, `mido`, `ffmpeg`). This is an hours-not-days fix.
3. "FluidSynth GM soundfont sounds cheap" — this is a soundfont-swap problem. Dropping in GeneralUser GS or a sampled orchestral SFZ library (via `sfizz`) instead of `fluid-soundfont-gm` is a Dockerfile change, not a research project, and directly targets the complaint about timbre.

None of the three problems is "the model can't compose/generate audio at all," which is the one category where a generative model would actually help — and that's also the one category this Mac cannot run at usable quality (see Q1). Spending effort standing up MusicGen/Stable Audio/ACE-Step under Docker-CPU would trade a few hours of DSP/config work for days of ML infrastructure work, on hardware that the models' own documentation says needs a GPU, to fix problems those models don't target. The same logic applies to art: the project's current CC0-remix + deterministic Pillow pipeline already produces clean, license-simple, fast output; nothing in the image-generation landscape below beats it on this hardware for pixel-art specifically.

**Concrete next steps, in priority order:**
1. Add CC10 (pan) / CC7 (volume) MIDI events per part in the `music21` script, spread the existing voices across the stereo field, and gain-stage relative to General MIDI's 0–127 default-100 convention (Q2).
2. Swap `fluid-soundfont-gm` for **GeneralUser GS** in `tools/composer/Dockerfile` (same FluidSynth CLI, one soundfont-file change, permissive license, all instruments in one bank) (Q3).
3. If GeneralUser GS's orchestral timbre still isn't enough, try `sfizz` + a CC0 sampled orchestral library (VCSL or Sonatina Symphonic Orchestra) — more setup than a soundfont swap, still no GPU/model work (Q3).
4. Leave the CC0 art pipeline alone; it's already the practical choice for this hardware (Q4).
5. Do not budget time on MusicGen/Stable Audio/ACE-Step/SDXL for production. If AI image ideation is ever wanted, the existing SD1.5-pixel-checkpoint recommendation in the 2026-08-07 doc remains the ceiling, unchanged by this pass.

## Q1 — Local AI music/audio generation models on an 8 GB Apple Silicon Mac

Assume ~4–5 GB usable headroom after macOS + Docker VM overhead, and that Docker Desktop on macOS gives Linux containers **no Metal/MPS GPU access** — a Linux ARM64 container here is a CPU-only workload regardless of the host chip ([Docker GPU support docs](https://docs.docker.com/desktop/features/gpu/), [PyTorch MPS backend docs](https://docs.pytorch.org/docs/stable/notes/mps.html)) — a constraint the prior 2026-08-07 doc already established and this pass confirms still holds.

**MusicGen (AudioCraft, Meta).** The official docs and model cards confirm five published checkpoints: **small (300M)**, **medium (1.5B)**, **large (3.3B)**, **melody (1.5B, text+melody conditioning)**, and **melody-large (3.3B)** — [`facebook/musicgen-small`](https://huggingface.co/facebook/musicgen-small), [`facebook/musicgen-melody`](https://huggingface.co/facebook/musicgen-melody), [`facebook/musicgen-large`](https://huggingface.co/facebook/musicgen-large), and the official [AudioCraft MUSICGEN.md](https://github.com/facebookresearch/audiocraft/blob/main/docs/MUSICGEN.md), which states verbatim: **"AudioCraft requires a GPU with at least 16 GB of memory for running inference with the medium-sized models (~1.5B parameters)"** and that only `small` is realistic on constrained hardware, with no mention anywhere of CPU inference or quantization as a supported path. Weights for every size are **CC-BY-NC 4.0** (non-commercial) per the same model cards; code is MIT. No official GGUF or MLX-native port of MusicGen exists — a GGUF search on Hugging Face turned up unrelated models (`ChatMusician-GGUF`, a text LLM; `Minimax-Music3-GGUF`, a different model) but nothing for MusicGen itself. **Verdict: even `small` (300M) is a CPU-inference gamble on 8 GB with no official low-footprint path, and the CC-BY-NC license already rules it out for anything shipped commercially; nothing feasible exists here for production use.**

**Stable Audio Open 1.0 (Stability AI).** [`stabilityai/stable-audio-open-1.0`](https://huggingface.co/stabilityai/stable-audio-open-1.0) states **1B params**, a transformer-diffusion audio architecture, PyTorch 2.5+, and CUDA-oriented example code with no CPU/Apple Silicon guidance. License is the **Stability AI Community License** — free under $1M annual revenue with registration, per the license terms already logged in the 2026-08-07 doc. No MLX or Core ML port exists on Hugging Face as of this research. **Verdict: too large/slow for CPU-only Docker, and the licensing overhead is disproportionate to a solo course project.**

**ACE-Step / ACE-Step 1.5.** This is the one place local Apple-Silicon-native tooling for music generation genuinely exists. [`mlx-community/ACE-Step1.5-MLX-4bit`](https://huggingface.co/mlx-community/ACE-Step1.5-MLX-4bit) is a real MLX port: **0.6B params**, 4-bit-quantized decoder/encoder (group_size=64), stated footprint **"2.2GB main model + 0.7GB VAE + 2.4GB text encoder"** ≈ **5.3 GB total** — technically within the 8 GB ceiling but consuming essentially all of the assumed 4–5 GB headroom by itself, leaving no room for the game/Docker/OS concurrently, and the model card doesn't state license terms for the underlying weights (needs separate verification against the upstream ACE-Step repo before any use). A non-quantized full-precision ACE-Step-1.5-MLX variant also exists but is larger still. **Verdict: the only "runs on this Mac" candidate found for music generation, but it would monopolize the machine's entire usable RAM for one render, still needs its license verified, and (per Q1's framing) doesn't address any of the three specific rejection reasons — none of which is "we have no music," so this isn't the fix needed even where it's technically possible.**

**Small symbolic/MIDI-generation models.** Real Hugging Face model cards exist and were checked directly, correcting an initial assumption that this space is mostly noise:
- [`Metacreation/MIDI-GPT`](https://huggingface.co/Metacreation/MIDI-GPT) — GPT-2-based, multitrack, bar-level infill and attribute-conditioned (instrument/style/density/polyphony) generation, from the [official MIDI-GPT paper/repo](https://github.com/Metacreation-Lab/MIDI-GPT). No single param count is published on the card (GPT-2-scale, so likely in the 100M–800M range depending on variant) — **I could not verify an exact parameter count from the primary source.**
- [`loubb/aria-medium-base`](https://huggingface.co/loubb/aria-medium-base) — **0.7B params**, LLaMA-3.2-1B architecture, Apache-2.0, solo-piano MIDI continuation (not multitrack composition). Genuinely small enough to consider running under Docker CPU for experimentation, but it continues existing piano MIDI rather than composing from a mood/tempo/instrumentation brief the way Composer's `music21` script does.
- [`amaai-lab/text2midi`](https://huggingface.co/amaai-lab/text2midi) — Transformer decoder (768 hidden dim, 8 heads, 18 layers) + a `flan-t5-base` text encoder, Apache-2.0, and its model card explicitly states **"support[s] inference on CUDA, MPS and cpu"** — the only model in this whole survey with an official, first-party CPU-inference claim. No exact total parameter count published (T5-base alone is ~220M, plus the custom decoder).

**Verdict on symbolic models:** these are real, licensed permissively, and technically plausible on this Mac's CPU — but every one of them generates or continues MIDI *from a text prompt or a piano seed*, not from music21's structured, notation-level brief-following process Composer already uses successfully (per the boss-1 track's Heckler-cleared gate, `docs/agents/composer/log.md`). Swapping a deterministic, auditable, already-working notation pipeline for a black-box text-to-MIDI model would trade control and reproducibility for a capability the project doesn't need — Composer's actual problem is compositional judgment and instrumentation choices, which a small autoregressive model would not obviously improve over deliberate `music21` authoring, and which none of these cards claim to solve.

## Q2 — Fixing the mixing problem (DSP, not ML)

This is confirmed as a DSP problem: research turned up no practically-runnable local FOSS auto-mixing tool, only academic research code.

**MIDI-level fix (do this first, inside `music21`/`mido` before rendering).** Every MIDI channel supports **CC7 (channel volume)** and **CC10 (pan)** as standard Control Change messages — the MIDI Association's own [Control Change explainer](https://midi.org/community/getting-started-with-midi-1/help-understanding-midi-volume-commands) and the [General MIDI Wikipedia summary of the MMA/JMSC spec](https://en.wikipedia.org/wiki/General_MIDI) confirm CC7 = channel volume and CC10 = pan as the GM-standard controllers every GM-compliant synth (including FluidSynth) must honor. Concretely: before rendering, each of Composer's parts (cello, harp, pad, bells, horn, trombone, timpani in the boss-1 track) can get an explicit CC10 pan value (e.g., melody centered, harp panned left-of-center, pad wide/centered, brass panned right) and a CC7 volume scaled relative to its role (melody and brass loudest, pad/ostinato quieter) — `mido` (already a Composer dependency) can insert these as raw `control_change` messages, or `music21`'s own `volume`/`dynamics` model can be baked in before MIDI export (see [`music21.volume` module docs](https://music21.org/music21docs/moduleReference/moduleVolume.html) and [`music21.midi.translate`](https://music21.org/music21docs/moduleReference/moduleMidiTranslate.html), which document how realized dynamics/volume propagate to MIDI velocity — note this affects velocity/loudness, not pan; pan needs an explicit CC10 message via `mido` or a raw `music21.midi.MidiEvent`, since `music21` has no first-class "pan" property). This is a same-day change to the existing composition scripts, not a new tool.

**Post-render fix (ffmpeg, already in `tools/composer/Dockerfile`).** The official [ffmpeg `pan` filter docs](https://ffmpeg.org/ffmpeg-filters.html#pan) confirm the filter takes a `layout|c0=expr0|c1=expr1|...` syntax where each output channel is an expression combining input channels with gain multipliers — e.g., `pan=stereo|c0=0.8*c0|c1=0.6*c0+0.4*c1` to reposition a mono or poorly-balanced stereo source. Since FluidSynth renders each MIDI channel already positioned by its CC10 value into one interleaved stereo WAV, the `pan` filter is a second-pass safety net (e.g., widening or narrowing the existing stereo image) rather than the primary panning mechanism — the CC10 events at MIDI level are the more precise and more idiomatic fix, `pan` the coarse post-hoc correction if something still sounds off after that.

**Gain-staging convention.** No single "authoritative" numeric standard exists for orchestral gain-staging the way there is for, say, broadcast loudness (LUFS), but the General MIDI default-volume convention itself is documented: CC7 defaults to 100 (of 127) per-channel unless explicitly set, and the practical convention (consistent with standard audio-engineering practice, not a single citable spec) is to keep sustained/background voices 10–20% below lead/melody voices and to reserve headroom so the mixed peak doesn't clip after all channels sum — this is general audio-engineering practice rather than a single authoritative citable source, and I could not find one canonical primary-source document that pins exact dB targets for GM-orchestral mixing specifically; treat the values above as a starting point to tune by ear, not a spec to follow exactly.

**ML auto-mixing: exists in research form only, not practically runnable locally.** Christian Steinmetz et al.'s [`automix-toolkit`](https://github.com/csteinmetz1/automix-toolkit) (Differentiable Mixing Console / Wave-U-Net models) and the [DL4AM tutorial](https://github.com/dl4am/tutorial) are real, primary-source, open repos — but they're training/research code (PyTorch notebooks, trained on the ENST-drums dataset), not a packaged CLI tool a solo developer could point at a MIDI render and get a mixed WAV back. Standing this up would mean training or adapting a research model, which is strictly more ML infrastructure work than the MIDI CC7/CC10 + `ffmpeg pan` approach above, for a use case (small ensemble, already-known instrumentation) that doesn't need learned mixing decisions. **Verdict: skip the ML route entirely; the MIDI-level fix is faster, fully deterministic (matches the project's existing determinism discipline), and directly addresses the stated complaint.**

## Q3 — Better soundfonts/sample players than FluidR3_GM, Docker-CPU-only

**FluidR3_GM's actual status (what's currently used, per `tools/composer/Dockerfile`'s `fluid-soundfont-gm` package):** MIT-licensed, built by Frank Wen (2000–2002, 2008, 2013) partly from public-domain samples and partly from the author's own recordings, per the [official FluidR3_GM README](https://member.keymusician.com/Member/FluidR3_GM/README.html) and its [Internet Archive listing](https://archive.org/details/fluidr3-gm-gs). It's a generalist, mixed-quality-by-instrument GM bank, not curated for orchestral realism — consistent with the developer's "sounds cheap" reaction.

**GeneralUser GS (S. Christian Collins) — recommended first swap.** Per the [official page](https://schristiancollins.com/generaluser.php) and its documented terms, GeneralUser GS may be used "without restriction for your own music creation, private or commercial," inherits its component samples' rights (mostly original recordings, with the author noting some samples' provenance is uncertain from the bank's non-published origins — worth a quick license re-check before shipping, per the project's own art/asset provenance discipline), and is a single ~30 MB GM/GS bank widely regarded as a quality step up from FluidR3 for general use. Same FluidSynth CLI (`fluidsynth -ni generaluser-gs.sf2 ...`), same Docker image, one file swap in the Dockerfile.

**Musyng Kite** — CC BY-SA 3.0 (per multiple secondary listings, e.g. [Polyphone's listing](https://www.polyphone.io/en/soundfonts/instrument-sets/258-musyng-kite) and the [midi-js-soundfonts repo](https://github.com/gleitz/midi-js-soundfonts)); one source describes it as "not meant to be redistributed... for commercial purpose" while allowing commercial *music made with it* — this is a genuinely confusing, inconsistently-stated license across mirrors and **I could not verify a single authoritative primary-source license text for it**; treat it as lower priority than GeneralUser GS until/unless someone reads the bank's own embedded license text directly.

**Timbres of Heaven** — GNU GPL 2.0 per multiple listings (e.g. [MidKar's TOH page](https://midkar.com/SoundFonts/TOH.html)), large (~1 GB+), GPL's copyleft terms are a heavier fit for a game-asset context than GeneralUser GS's unrestricted terms; viable but a secondary option.

**sfizz — a real, headless, CPU-only SFZ player, confirmed viable for Docker.** The [official sfizz GitHub repo](https://github.com/sfztools/sfizz) confirms: BSD-2-Clause license, a C++ synth library with a JACK standalone client (so it can run without a GUI), and no GPU dependency stated anywhere. It has no built-in Docker image, but as a CLI/library tool it fits the same pattern as the FluidSynth Dockerfile already in use.

**Sample libraries to pair with sfizz — both genuinely CC0/permissive and orchestral:**
- **VCSL (Versilian Community Sample Library)** — CC0, per [Versilian Studios' own page](https://versilian-studios.com/vcsl/) and the [official GitHub repo](https://github.com/sgossner/VCSL) ("Open CC0 sample library"). Dozens of orchestral/world instruments with SFZ patches, explicitly license-clear for commercial use with no attribution required.
- **Sonatina Symphonic Orchestra (SSO)** — Creative Commons Sampling Plus 1.0 (per multiple listings including the [SFZ Instruments SSO page](https://sfzinstruments.github.io/orchestra/sso/)), maintained since 2017 by Peter Eastman at the [official `peastman/sso` GitHub repo](https://github.com/peastman/sso). Note Sampling Plus 1.0 is **not** as permissive as CC0 (it restricts direct sample redistribution/whole-work sampling in some cases) — worth a closer license read before committing to it over VCSL.

**Verdict:** GeneralUser GS is the lowest-effort, highest-confidence fix (one file swap, FluidSynth unchanged, clearly-stated commercial-use terms). If the FluidSynth-rendered timbre still isn't convincing after that, `sfizz` + VCSL is the next step up in realism, still CPU-only and Docker-compatible, at the cost of a new player binary and heavier sample assets to manage in the Docker build.

## Q4 — Pixel-art image generation on 8 GB Apple Silicon, and is CC0-remix already right?

**SDXL-Turbo.** [`stabilityai/sdxl-turbo`](https://huggingface.co/stabilityai/sdxl-turbo): 3B UNet params, `sai-nc-community` license (commercial use requires a separate Stability membership), and the model card's own example code explicitly supports MPS (`"switch to 'mps' for apple devices"`) — but that's native macOS PyTorch/MPS, not available inside a Docker Linux container on this Mac. No Core ML/MLX-native SDXL-Turbo port was found as a first-party artifact.

**Apple's own Core ML path — the one place 8 GB is officially declared workable.** The [official `apple/ml-stable-diffusion` README](https://github.com/apple/ml-stable-diffusion) directly answers "does this work on 8GB Macs": **"My Mac has 8GB RAM, should image generation work on my machine? Yes!"**, recommending the `CPU_AND_NE` compute unit and converting model components sequentially (not all at once) to avoid OOM during conversion. It states peak runtime memory "over 2 GB," and that weight compression (palettization) "reduces peak RAM usage by up to 75%." It supports SD 1.4/1.5/2/2.1-base/XL/SD3. This is real, Apple-authored evidence that image generation is technically possible on this exact RAM class — but it's Core ML (native macOS), not something that runs inside the project's Docker-only pipeline per ADR 0003, and it targets photographic/general SD checkpoints, not a pixel-art-specific one.

**mlx-examples (`ml-explore/mlx-examples`), also Apple-ecosystem-native, not Docker.** The [official stable_diffusion README](https://github.com/ml-explore/mlx-examples/blob/main/stable_diffusion/README.md) states plainly: **"the Stable Diffusion XL UNet alone has 2.6B parameters[,] in order to use it in devices with 8GB of RAM, quantization is practically necessary,"** and that quantizing the text encoder to 4-bit and the UNet to 8-bit **"allows generating images on an 8GB Mac Mini with no-swapping."** Supports SDXL, SDXL Turbo, and SD 2.1 (no SD1.5 confirmed in this example). Same caveat as Core ML: this is a native-macOS MLX program using the M1's GPU/Neural Engine directly — it cannot run inside a Linux Docker container on this machine, which is exactly the environment ADR 0003 requires for all creative tooling. Using it would mean either revising the ADR to allow a host-side exception for this one tool, or not using it.

**SD1.5 pixel-art LoRAs and SDXL pixel-art LoRAs on Hugging Face — real, verified repos, not guessed:**
- SDXL: [`nerijs/pixel-art-xl`](https://huggingface.co/nerijs/pixel-art-xl) (CreativeML OpenRAIL-M, targets `stable-diffusion-xl-base-1.0`, recommends 8x nearest-neighbor downscale post-generation for "pixel perfect" results), plus [`joachimsallstrom/aether-pixel-lora-for-sdxl`](https://huggingface.co/joachimsallstrom/aether-pixel-lora-for-sdxl) and [`ntc-ai/SDXL-LoRA-slider.pixel-art`](https://huggingface.co/ntc-ai/SDXL-LoRA-slider.pixel-art).
- SD1.5: [`artificialguybr/pixelartredmond-1-5v-pixel-art-loras-for-sd-1-5`](https://huggingface.co/artificialguybr/pixelartredmond-1-5v-pixel-art-loras-for-sd-1-5) and the previously-verified [`PublicPrompts/All-In-One-Pixel-Model`](https://huggingface.co/PublicPrompts/All-In-One-Pixel-Model) from the 2026-08-07 doc.
- All SDXL-based LoRAs inherit SDXL's 2.6B-parameter UNet and the same 8GB-needs-quantization ceiling `mlx-examples` documents above — meaningfully heavier than the SD1.5 route the prior research already scoped for Docker-CPU (roughly 5–7 GB live RAM, tens of minutes per image at 384–512px). SDXL pixel-art LoRAs are not a realistic addition to the Docker-CPU pipeline on this Mac; SD1.5 ones remain at the same "slow ideation only" tier the 2026-08-07 doc already assigned.

**Is CC0-remix + deterministic Pillow already the more practical choice? Yes, clearly, and this pass didn't find anything to overturn that.** Every genuinely fast/native path (Core ML, MLX) requires leaving Docker, which conflicts with ADR 0003's stated rationale (keeping creative exploration off the host to protect the 8 GB machine). Every Docker-compatible path (SD1.5 CPU inference) is tens-of-minutes-per-image, batch-1, and still needs manual pixel-cleanup afterward — Tilesmith's own log (`docs/agents/tilesmith/log.md`) already shows the CC0-remix and deterministic-Pillow treatments shipping same-day, reproducible, byte-identical output with full provenance tracking, which no diffusion-based path on this hardware can match for iteration speed or auditability. My own opinion, not just a restatement of the prior doc: for a solo course project with a real submission deadline, the fact that AI image generation is *technically possible* on an 8 GB Mac (Apple's own README says so) doesn't make it the right choice when the existing CC0/deterministic pipeline is faster, cheaper, license-simpler, and already produces shippable results — chasing the AI path here would be optimizing for novelty over the actual constraint (time, not asset quality ceiling).

## Uncertainty and conflicts found (not papered over)

- **MIDI-GPT's exact parameter count** could not be verified from its Hugging Face card or linked GitHub repo/paper abstract within this research pass — only its architecture family (GPT-2-based) and capabilities are confirmed.
- **Musyng Kite's license** is stated inconsistently across secondary sources (CC BY-SA 3.0 vs. a "no commercial redistribution of the bank itself" caveat) with no single primary license text read directly from the bank's own bundled documentation in this pass — flagged as lower-confidence, not resolved.
- **GeneralUser GS's full sample-provenance chain** is explicitly uncertain even per the author's own page (some samples' original source is unknown to the creator) — the license is unrestricted for now, but this is worth a quick recheck before any commercial ship, per this project's existing provenance-logging discipline for CC0/sourced assets.
- **A single authoritative numeric gain-staging standard for orchestral/GM mixing** does not appear to exist as one citable primary source; the recommendation above (headroom, relative lead-vs-background gain) reflects general audio-engineering convention, not a specific spec — flagged rather than asserted as gospel.
- **ACE-Step 1.5's underlying weight license** was not stated on the `mlx-community/ACE-Step1.5-MLX-4bit` card itself; only the upstream ACE-Step project's own license (not fetched in this pass) would confirm commercial-use terms, so this is noted as an open item rather than assumed permissive.
- The developer's own three rejection reasons (composition, mixing, timbre) were taken at face value from the task framing; this research did not re-listen to the actual rejected track, so the specific severity of each issue is the developer's judgment, not independently verified here.
